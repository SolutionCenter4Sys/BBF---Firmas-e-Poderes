Seção 01

O que isto não é (e o que é)

Não existe um comando do tipo npm install pipeline. Neste repositório o motor nunca foi escrito.

O README descreve o estado atual como Step 6 — Frontend MVP com Mock. Os dados vêm de src/lib/mocks.ts. O backend REST está previsto só no Step 12.

O “motor” é um orquestrador assíncrono: o upload não processa o PDF no clique. A API aceita o ficheiro (HTTP 202), grava o documento e uma fila + workers avançam os estágios (OCR → IA → canónico → decisão).

Hoje a UI só pinta o status. Sem API que mude esse status, o ficheiro enviado fica em pendente para sempre.

Seção 02

Por que o processamento para

Ao clicar em + Novo upload, o dashboard atual:

  1. Não envia o ficheiro a nenhum servidor (fetch / FormData inexistentes).
  2. Não guarda os bytes do PDF — só o nome do arquivo.
  3. Cria um cartão em memória / sessionStorage com status: "pendente".
  4. Mostra o banner “Pipeline iniciado” — mensagem enganosa: não há worker, timer nem fila.

A barra em PipelineStatusBar.tsx mapeia pendente apenas para o passo 1. Upload. Os documentos da lista que já aparecem “decididos” são fixtures estáticos em mocks.ts, não passaram por upload real.

Seção 03

O que o motor precisa fazer

1 Upload→ 2 OCR→ 3 IA Gen / NER→ 4 Canónico→ 5 Decisão
Ordem Estágio (UI) Status no código Trabalho real
1 Upload pendente Guardar ficheiro, antivírus, gerar documentId e correlationId
2 OCR processando_ocr PDF/imagem → texto + páginas + CER

Serviços que o próprio mock já nomeia (observabilidade e custos):

Seção 04

Contrato já desenhado no frontend

O array openApiEndpoints em src/lib/mocks.ts é o contrato do Step 12. Instalar o motor = implementar estes endpoints + workers, e o Next deixar de usar sessionStorage.

Upload — inicia o pipeline

POST /v1/documents
Content-Type: multipart/form-data
X-Correlation-Id: opcional

file = <PDF ou imagem, até 50 MB>

Resposta 202 Accepted:

{
  "documentId": "doc_xxx",
  "status": "pendente",
  "uploadedAt": "2026-04-30T..."
}

Polling do progresso

GET /v1/documents/{documentId}/status

Devolve o DocStatus atual. A UI consulta até chegar a decidido, falha ou revisao_humana.

Outros endpoints já previstos

  • GET /v1/authority/decision — decisão para jornada consumidora
  • POST /v1/decision/evaluate — avaliação interna (UI)
  • POST /v1/decision/{id}/replay — replay determinístico
  • GET /v1/audit/trail — trilha por correlationId
  • GET /v1/verification/health — saúde das fontes oficiais

Seção 05

Dois caminhos: demo vs. motor real

A) Simulador local (demo)

Não chama OCR nem Junta. Um timer no browser (ou uma API Route do Next) muda o status:

pendente → processando_ocr → processando_iagen → canonico_pronto → decidido

Copia sócios/poderes de um mock (ex.: doc_001). A barra “anda”. Não lê o PDF. Não é o Step 12. Serve para usabilidade e apresentação.

B) Motor real (produto)

Vários processos + fila + storage + secrets. O ficheiro é processado de facto.

Não cabe num npm install no frontend. É um projeto de backend (orquestração + 4–5 serviços), alinhado ao contrato da seção 04.

Seção 06

Como montar o motor real (passos)

Passo 0 — Stack (este repo é só UI)

O frontend é Next.js 14. O motor não deve viver só no browser: PDF + chaves de IA no cliente é inseguro e incompatível com LGPD.

Padrão alinhado ao mock e ao deploy atual (Azure Static Web Apps):

  • API HTTP (Node, Java ou .NET — o que o BBF padronizar)
  • Fila (Azure Service Bus, RabbitMQ ou Redis)
  • Object storage (Azure Blob)
  • Base relacional (Postgres ou SQL Server) para documento, status, canónico e auditoria

Passo 1 — Persistência mínima

TabelaConteúdo
documentsid, nome, hash, status, correlation_id, uploaded_by
document_blobsURI no Blob Storage
extractionstexto OCR, scores ocr / iagen / ner
canonicalJSON pessoas/poderes (ver canonicalSchemaPreview)
decisionsresultado + motivos + snapshot de regras
audit_eventsappend-only: uploaded, ocr.completed, etc.

Passo 2 — Implementar POST /v1/documents

  1. Validar tipo (PDF/imagem) e tamanho (50 MB).
  2. Antivírus (já prometido no dropzone da UI).
  3. Gravar blob + hash.
  4. Inserir documento com status = pendente.
  5. Publicar na fila: { documentId, correlationId }.
  6. Responder 202 — não esperar o OCR.

O dashboard passa a chamar esta API em vez de addSessionDocument.

Passo 3 — Worker / orquestrador (o motor)

Um processo consome a fila e corre os estágios em série (saga com compensação se um passo falhar):

pendente
  → processando_ocr        (Document AI ou Tesseract)
  → processando_iagen      (LLM + schema de extração)
  → processando_ner        (CPF, cargo, limite, N de M)
  → canonico_pronto        (normalizar para o schema)
  → validacao_oficial      (Junta / Receita + circuit breaker)
  → decision-engine        (RN01, TH01, …)
  → decidido | revisao_humana | falha

A cada estágio o worker deve:

  1. Atualizar status na base.
  2. Escrever evento de auditoria.
  3. Se score < threshold (regra TH01): ir para revisao_humana e parar até a fila humana.
  4. Se exceção: falha + devolver correlationId (já previsto no detalhe de falha da UI).

GET /v1/documents/{id}/status apenas lê a base. O frontend faz poll (ex.: a cada 2 s) ou WebSocket.

Passo 4 — “Instalar” os motores de cada estágio

Aqui sim há instalações / contratações — uma por estágio, não um produto único.

Estágio O que se instala ou contrata Nota deste projeto
OCR Google Document AI e/ou Tesseract O mock de custo já cita os dois
IA Gen Azure OpenAI, Vertex ou API interna BBF PII — dados no tenant do banco
NER Modelo próprio, spaCy ou o mesmo LLM com schema Status processando_ner
Fontes oficiais Conectores Junta / Receita / PEP Tela /sources/health + circuit breaker
Regras Código, Drools ou serviço interno Catálogo em /admin/rules
Fila + Blob Azure Service Bus + Blob Storage Alinhado ao workflow GitHub → SWA

Cada integração precisa de conta cloud, secret em Key Vault / variável de ambiente (nunca no frontend) e um adapter no orchestration-api.

Laboratório de OCR (não é produção bancária)

pip install pypdf pytesseract
# + Tesseract OCR instalado no Windows

Isto não substitui Document AI em produção. Serve só para provar o fluxo localmente.

Seção 07

Como ligar o Next.js ao motor

  1. Definir base da API, ex.: NEXT_PUBLIC_API_BASE=http://localhost:8080 (ou BFF em src/app/api/ como proxy).
  2. Trocar ingestFiles por POST /v1/documents com FormData.
  3. Trocar a lista e o detalhe (documents / findDocument) por GET reais.
  4. Fazer polling em /documents/[id] até status terminal.
  5. Auth: o mock já prevê OAuth2 e scopes (401 / 403).

Enquanto essa API não existir, o Step 12 não está instalado.

Seção 09

O que não resolve o problema

  • Instalar mais uma biblioteca no Next com npm install
  • Enviar o mesmo PDF de novo
  • Azure Static Web Apps — só faz host da interface
  • BMAD / agentes de review — geram documentação, não OCR

Seção 10

Recomendação prática

ObjetivoO que fazer
Demo / usabilidade (a barra anda) Simulador no frontend (timers + mocks). Horas, não semanas.
Homologar extração de um PDF real Worker mínimo: POST /v1/documents + Tesseract ou Document AI + poll de status.
Produção BBF (Step 12) Orquestrador + serviços + Blob + fila + OAuth + Junta/Receita + motor de regras. Projeto de backend.

Resumo em uma frase

O motor em falta é o backend assíncrono do contrato /v1/documents mais os workers OCR → IA → canónico → decisão. Ou se simula o avanço de status, ou se constrói essa API. Não se instala como dependência deste repositório.
